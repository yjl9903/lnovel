# 文档优先的开发流程

本流程参考相邻 `pushc/AGENTS.md` 与 `napcatc/AGENTS.md` 的 Documentation-First Workflow，并保留本仓库对 README 和全局介绍文案的审批约定。

## 开始修改前

1. 阅读 [文档索引](index.md) 和相关架构，找到现有接口、状态所有者及约束。
2. 核对对应源码、配置和测试，区分当前实现、已有设计决策与尚未实现的目标。
3. 文档与代码不一致时先查明原因：过时说明按现状修正；实现偏离已确认设计时按需求修复。不要直接把偏差当成新的设计。
4. 明确本次行为变化和验收方式。涉及既有 API、RSS 地址或数据库语义时明确兼容性要求，沿用用户已确认的决定。

文档优先不要求每个小改动都创建计划，也不要求每次技术说明更新都等待审批。

## 何时写计划

跨模块调整、持久化语义变化或影响较大的需求，在 `docs/plan/<YYMMDD>-<requirement-name>.md` 记录方案。同一需求优先更新已有计划，主题真正变化时才新建文件。局部修复或文档勘误直接修改对应文档即可。

计划至少包含：

- 背景、目标和本次范围；
- 关键决策、需要确认的事项及兼容性处理；
- 技术方案、涉及的模块和文档；
- 验收场景、验证命令及完成状态。

待确认内容明确标注，不得写成用户已批准的决定。实现中方案发生变化时更新计划；交付后将最终行为落实到架构文档，历史取舍留在计划中。

## 实现与交付

按模块边界实现，并在同一次变更中维护受影响的架构、运行说明、请求示例和测试。优先验证可观察结果，验证范围见 [测试说明](testing.md)。

交付前确认：

- 文档中的接口、配置、命令、状态和模块责任与最终代码一致；
- 文档链接可解析，示例指向存在的入口；
- 测试结果与未覆盖部分如实记录，不把测试替身的成功当成在线服务可用；
- 计划不再将已完成内容标成待办，架构文档不混入已弃用方案。

## README 与介绍文案

项目名称、简介、SEO description 和分享摘要优先逐字复用用户编写或确认的 `package.json`、`README.md` 内容，并注明来源。代理之前写过的内容不自动成为已批准来源。

新增或改写这些文案，以及新增、修改、删除、移动任何 `README.md`，先展示具体内容、使用位置及理由，获得明确批准后再写入。审批范围仅限已确认的内容。普通技术说明直接维护在 `docs/`，无需为了增加开发文档而扩写项目介绍。
